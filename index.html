The issue problem

A public report is not automatically a reproduced defect.

Issue queues mix current failures with resolved reports, incomplete reproduction steps, stale assumptions, and questions that belong upstream.

The smallest useful first step is to record what the public evidence establishes, what it does not, and which fact would change the decision.

01

Is the reported state still current?

Check linked changes, releases, and issue history before assuming implementation is needed.

02

Is the failure documented or reproduced?

Keep reporter evidence distinct from independently verified runtime behavior.

03

What fact would change the decision?

Name the decisive evidence gap instead of hiding uncertainty inside a summary.

04

What is the smallest next check?

Prefer a bounded acceptance check or source review before open-ended implementation.

Scope discipline

Useful within a narrow public lane.

Designed for

  • One public GitHub software issue
  • Public source and issue-state capture
  • Distinguishing reported, source-supported, and reproduced claims
  • Reviewable, source-linked handoffs

Outside the lane

  • Security vulnerabilities or embargoed disclosures
  • Private repositories, credentials, customer data, or confidential logs
  • Target-code execution or production access
  • Repository affiliation, endorsement, or outcome guarantees
